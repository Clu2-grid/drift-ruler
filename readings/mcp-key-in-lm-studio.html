Where a remote MCP server's key actually lives in LM Studio

One page. Read in a minute. Checked against LM Studio's own docs, 19, 20, 21 and 22 Nov 2026.

Short answer: if you are adding the server by hand, in mcp.json, as a plain text line inside that server's headers block. Not in a settings screen, not in the model config, not in an env field.

If the server supports OAuth, there may be no key of yours in the file at all. That case is the third section below.

{
  "mcpServers": {
    "your-remote-server": {
      "url": "https://example.com/mcp",
      "headers": {
        "Authorization": "Bearer YOUR_TOKEN_HERE"
      }
    }
  }
}

That is the shape LM Studio documents for a remote server. It follows Cursor's mcp.json notation, so if you have seen Cursor examples, it is the same idea. The token sits in headers, spelled Authorization, with Bearer and a space before the token.

Getting to that file

  • Requires LM Studio 0.3.17 (b10) or later. Earlier versions are not an MCP host at all.
  • In the app, open the Program tab in the right sidebar.
  • Click Install, then Edit mcp.json. The in-app editor opens the file.
  • Paste the server block inside mcpServers, save, and the server appears in the app.

Three ways this bites

  • Wrong block. A local server example uses command, args and env. A remote server uses url and headers. Copying the local shape and dropping a key in env does nothing for a remote URL.
  • Wrong header. The name is Authorization, and the value is Bearer <TOKEN>. Some servers use a different header name; check that server's own docs rather than assuming.
  • It is plain text on your disk. Not a keychain entry. Anyone with access to that file can read the token, and if you sync your LM Studio config to a repo or a backup, you are syncing the token. Treat that file like a password file. The bring-your-own-OAuth shape further down puts a client secret in the same file.

The step the docs bury in a footnote

Straight from the docs page, and easy to skim past: when you add a server by hand, paste only what sits between "mcpServers": { and its closing }. Pasting the whole thing in leaves you with a mcpServers block inside mcpServers, the server never loads, and nothing tells you why. If you copied an example wholesale and the server is missing, open the file and look for a doubled key. That is the first place to look before you touch the header line.

Two cautions the same page gives, worth repeating

  • Do not install from a source you cannot read. An MCP server can run code, touch your local files, and use your connection.
  • Some servers were built for Claude, ChatGPT or Gemini and will eat your context. On a local model that shows up as a sudden overflow or a model that stops mid-answer, long before any error.

Three credential shapes, and the one that is now corrected

Correction, 22 Nov 2026, to myself. A day ago this page said it did not know whether LM Studio implements MCP's OAuth flow. It does, and it is documented. Recorded here rather than quietly swapped out: the earlier line was wrong, and the wrongness is the useful part. Any page about moving parts is a claim with a date on it.

LM Studio's own docs, read 22 Nov 2026, describe three ways a remote server gets a credential:

  • A static token you paste. The headers / Authorization block at the top of this page. Plain text in this file, yours to manage and to leak.
  • OAuth through the app. For supported integrations, adding one opens a browser window, you approve, and LM Studio "stores the token securely" and exposes the tools. The docs do not say where that token is stored, which is the line on this page most likely to be wrong. If you have found the file, say so and I will put it here.
  • Bring your own OAuth app. For services without dynamic client registration, or that need a whitelisted redirect URI, add an auth object to the server entry instead of headers, with CLIENT_ID and CLIENT_SECRET. The redirect to register is http://127.0.0.1:33389/mcp-oauth-callback. Note what that shape costs: the client secret is again plain text in mcp.json.

So "where does the key live" has three answers, and only one of them is a secret on your disk that you chose to put there.

What the protocol itself says

MCP's authorization spec, read 21 Nov 2026: authorization is optional. HTTP-based transports should conform to its OAuth flow, and stdio servers should not, instead retrieving credentials from the environment. Two things follow.

  • The plaintext Bearer line is the shape LM Studio's app docs show for hand-added servers, not the only shape the protocol allows. The OAuth paths above are the other shape, and they exist in the app.
  • The protocol's own answer for local servers is the environment, which is why a local example carries an env block. A hand-added remote server with its key in headers gets no such separation. The secret is in the config file, and the config file is the thing people back up and sync.

What to do when tools do not show up

Check the header line first, character by character, before you touch anything else. A mangled Bearer (missing space, extra quote) fails quietly. Then check the server block's shape: url plus headers for remote, command plus args for local. Only after both of those is it worth suspecting the server.
